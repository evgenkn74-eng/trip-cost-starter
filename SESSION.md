# Сессия работы с ИИ-агентом

Журнал того, как делалось задание: какие инструменты, ключевые промпты, что предложил ИИ, что я принял, а что
исправил или отверг. Итог работы и решения по заданию описаны в [README.md](README.md).

## Актуальное состояние на 27.11.2026

- Реализованы распределение стоимости рейса, API долей и таблица в карточке рейса; API предпросмотра и применения месячных счетов; экран пересчёта.
- Основной поток биллинга: `billing_preview.php` вызывает `billing_preview_data()`, интерфейс показывает результат и по подтверждению отправляет POST в `billing_apply.php`, который вызывает `billing_apply_period()`.
- Предпросмотр и применение проверяют, нет ли у клиента нескольких счетов за период. При дубликате оба API возвращают JSON-ошибку; транзакция применения откатывается.
- Предпросмотр считает `changes` по новым счетам и черновикам с изменившейся общей суммой. Применение сравнивает ещё и строки рейсов. Поэтому одинаковая итоговая сумма при другой раскладке строк остаётся известным ограничением: кнопка может быть выключена, хотя применение обновило бы строки. Допущение описано в README.
- Октябрь 2026 пересчитан; результаты до и после приведены в README. Автотестов нет, API и экран проверялись вручную.

## Инструменты и роли

| Инструмент | Для чего использовал |
|---|---|
| **GitHub Copilot (чат-агент в VS Code)** | Работа прямо в репозитории: чтение задания и кода, правки файлов, API `trip_split`, блок в карточке рейса, статичный макет экрана, ревью готового кода |
| **Claude (claude.ai)** | Обсуждение вне репозитория: анализ данных и вопросы заказчику, проектирование алгоритма распределения копеек, структура JSON предпросмотра, код `billing_preview_data`, `billing_apply_period` и `billing.js`, проверка макета и итогов |

Промпты я надиктовывал голосом, поэтому ниже они даны в очищенном виде (без ошибок распознавания речи), смысл сохранён.

## Правила, которые я задал агентам

- Деньги суммируем в целых копейках: сначала всё переводим в копейки, считаем, и только на выводе переводим в рубли.
- Параметры запроса в SQL только через `prepare`, а не подстановкой в строку.
- Несколько связанных записей в базу делаем в одной транзакции, ошибки ловим через `try/catch` с откатом.
- PHP-переменные в стиле `snake_case`. Единый стиль ответов API: `json_out`.
- Сначала простая рабочая версия, рефакторинг отдельным шагом. ИИ не додумывает: если неясно, задаёт вопрос.
## Ход работы

### 1. Подготовка (Copilot)
- **Промпт:** «Прочитай README и HTML задания из `.my`, создай в корне `SESSION.md`: наш журнал сессии.»
- Агент прочитал README, задание и мои заметки (`план.txt`), создал первый `SESSION.md`. По моей просьбе подключил
  `composer` (пустой `require`) и autoload; позже в `bootstrap.php` добавлен обработчик ошибок Whoops.
### 2. Расчёт долей (Copilot, затем Claude)
- **Промпт:** «Функция распределяет стоимость поездки, умножая стоимость на долю и округляя до двух знаков, поэтому
  сумма счетов меньше стоимости рейса на 1-2 копейки.»
- Агент нашёл причину (независимое округление каждой доли) и предложил расчёт в целых копейках и граммах с раздачей
  остатка. Я оценил новую функцию `calc_share_by_weight`, попросил записать изменения в `SESSION.md`.
- **Промпт:** «Напиши `calc_share_by_volume` по аналогии с весом. Рефакторинг позже, сейчас только функцию.»
  Агент сначала предлагал объединить функции в одну, я отказался: делаем по очереди.
- **Моя правка:** агент называл единицу объёма «литры». Мне это название показалось неподходящим для груза; обсудили,
  коэффициент ×1000 оставил, название заменил на нейтральное (в итоге тысячные доли м³).
- **Моя правка поведения агента:** он каждый раз предлагал мне запускать PHP-команды. Я попросил так не делать.
- **Claude:** объяснил метод наибольших остатков (почему остаток нужен как мера справедливости, а не случайность и не
  порядок по `client_id`), проверил алгоритм на всех рейсах базы (сумма долей = стоимость рейса). Затем по двум моим
  функциям (вес и объём) выделил общие части: `get_trip_cost_kop`, `get_trip_client_rows`, `distribute_cost`,
  `build_share_result`, и это вошло в код. Диспетчер `calc_share` (объём, если он > 0 у всех грузов рейса, иначе вес)
  предложил я, Claude уточнил проверку `COUNT(*)` / `SUM(volume_m3 IS NULL OR volume_m3 <= 0)`.

### 3. API долей рейса (Copilot)
- **Промпт:** «Посмотри соседний `trips.php` и по его стилю опиши свою реализацию в файле-черновике. Если что-то
  неясно, не додумывай, задавай вопросы.» Затем: «`share` округлить до 4 знаков; `volume_m3` отдавать числом только
  если он не `null` и не равен нулю.»
- Реализован `public/api/trip_split.php`; коммит «Добавить API распределения стоимости рейса».
### 4. Блок в карточке рейса (Copilot, Claude)
- Сначала статичная таблица двумя строками (без PHP), затем колонка «Распределено по» (я просил придумать
  понятное пользователю название вместо «базис»), затем `trip_split.js`: берёт `data-trip-id` из атрибута таблицы и
  заполняет её из API; обработка `404`.
- **Моя правка:** агент считал итоги с лишним переводом в копейки и обратно. Я упростил: итог считаем в копейках и
  делим на 100 только при выводе (отсюда правило про деньги).
- **Claude:** при проверке заметил, что задание требует в итоговой строке и сумму по клиентам, и стоимость рейса;
  добавили вторую итоговую строку.
### 5. Экран «Счета за месяц» (Copilot строил верстку, Claude проверял)
- Я делал макет поэтапно: селект месяцев, «Показать»/«Применить», таблица «было / стало», знаки и цвета разницы,
  ссылки на счета, колонка статуса, серые строки отправленных, зелёные новых; затем блок «Итоги за месяц».
  Стили в `app.css` сгруппировал, повторы убрал.
- **Claude:** по скринам предлагал: статус счёта обязателен, три итоговые строки (общий итог, будет пересчитано,
  не будет пересчитано), сверка с суммой всех рейсов, состояния экрана.
- **Что я отклонил:** Claude предложил колонку «основание расчёта» по клиенту. Я возразил: у клиента несколько
  рейсов, у одних расчёт по объёму, у других по весу, единого значения нет. Колонку убрали, основание оставили на
  уровне рейса. Claude предложил заменить «Все месяцы» на реальные месяцы; я оставил как в остальных разделах
  проекта (свою практику не навязывать месяц по умолчанию).
- **Моя идея:** сначала делать визуальную часть на заглушке API, потом подключать расчёты.
### 6. API предпросмотра и применения (Claude, интеграция моя)
- **Промпт:** «Оцени мою структуру массива ответа: подходит ли под заполнение макета, что добавить, убрать, переименовать.»
  Структуру ответа я описал, Claude дал свою версию с комментариями к каждому полю; я переименовал блоки по формату
  задания (`clients`, `before`, `after`) и `cost_trips`.
- **Промпт:** «Мне нужен `billing_preview.php`; проверку параметра оставь как есть, остальное перепиши так, чтобы
  массив заполнился реальными данными и вывелся через `json_out`.» Claude написал `billing_preview_data` в `lib/billing.php`
  и тонкий файл эндпоинта; я проверил результат на октябре.
- **Мои правки:** закомментировал и убрал лишний `will_write` по клиентам и группам (оставил только в итогах),
  вернул `action`, переписал комментарии. По рекомендации Claude `billing_run.php` теперь только перенаправляет на новый
  экран: стартовое формирование перезаписывало и отправленные счета, что противоречит ответу заказчика.
- **Промпт:** «Начинаем `billing_apply`» Claude написал `billing_apply_period` (транзакция,
  пропуск отправленных, повторный вызов не пишет в базу) и проверил идемпотентность на копии базы в Python. Для SQLite
  дату создания ставит сама база.
- **Промпт:** «Что писать вместо `TODO` в `billing.js`?» Claude дал `$.post`, плашку результата и перезагрузку
  предпросмотра; затем я попросил `billing.js`, который выводит обе таблицы по JSON.
### 7. Ревью и исправления (Copilot проверяет код, написанный в Claude)
Я попросил Copilot отдельно проверить `lib/billing.php`, `api/billing_apply.php`, `api/billing_preview.php`, `js/billing.js`.
Замечания и мои решения:

| Замечание | Решение |
|---|---|
| Рядом осталась старая `billing_run_period`; в ней копейки суммируются дробными | Это функция стартового проекта, новый экран её не вызывает; замечание снято |
| Вес может быть нулевым | Вес заполнен и положителен; отсутствующий или нулевой объём переключает расчёт на вес |
| У клиента может быть несколько счетов за период | Принято: предпросмотр и применение обнаруживают повтор и выбрасывают исключение; API возвращают JSON-ошибку |
| Кнопка «Применить» включалась для черновика с уже совпадающей суммой | `changes` теперь учитывает только новые счета и черновики с отличающейся общей суммой |
| Предпросмотр и применение сравнивают черновик по-разному | Ограничение оставлено: предпросмотр сравнивает суммы, применение дополнительно сравнивает строки рейсов. При одинаковой сумме и изменившихся строках кнопка может остаться выключенной; допущение описано в README |
| Пункт «Все месяцы» без значения | Оставлен намеренно, по аналогии с другими разделами проекта |

### 8. Октябрь и README
- Октябрь 2026 применён через `billing_apply`: пересчитано 3 черновика, 3 отправленных не тронуты, сумма по новому
  правилу равна стоимости рейсов (454 610,80), после применения счета дают 517 702,90 (разница с рейсами сидит в
  отправленных, это решение заказчика). Таблицы «до» и «после» в README.
- README дописан с помощью Claude: сверка исходного проекта с текущим, итог «было и стало», допущения и ограничения.
## Где ИИ ошибся или был неточен

- Copilot предлагал выполнить проверку вручную после каждого кода; Claude на первом анализе данных назвал неверное
  число рейсов с пропусками объёма. При подготовке README пересчитано по базе: **7 рейсов из 12**. Claude один раз описал `calc_share` по версии из архива, а не по
  той, что у меня была; я поправил и продолжили от моей версии.
- Предложения, которые я не принял: объединить две функции расчёта в одну до того, как они написаны; колонка
  «основание» по клиенту; замена «Все месяцы»; исправление сравнения строк в предпросмотре.
## Что проверено вручную

API `trip_split` по рейсам 3, 6, 7 (бывшие рейсы с потерей копейки), `billing_preview` и `billing_apply` на октябре
(повторный вызов даёт `unchanged: 3`, `changes = 0`), экран «Счета за месяц» до и после применения.
Автотестов нет.
