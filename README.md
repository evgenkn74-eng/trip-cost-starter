# Рейсы и счета

Небольшая система учёта рейсов сборных грузов и счетов клиентам.

## Запуск

Нужен PHP 8.2+ с расширением `pdo_sqlite`.

```bash
composer install
php bin/reset-db.php
php -S localhost:8000 -t public
```

Открыть http://localhost:8000.

`composer install` ставит только инструменты отладки (страница ошибок Whoops); для работы расчётов они не нужны.

То же через Docker:

```bash
docker run --rm -it -p 8000:8000 -v "$PWD":/app -w /app php:8.4-cli \
    sh -c "php bin/reset-db.php && php -S 0.0.0.0:8000 -t public"
```

`php bin/reset-db.php` пересоздаёт базу `data/app.sqlite` из `data/schema.sql` и `data/seed.sql`. Так можно вернуть
исходные данные в любой момент. **Важно:** в сданной базе октябрь 2026 уже пересчитан по новому правилу (см. ниже),
после `reset-db.php` он снова будет в исходном виде, и его можно пересчитать заново через экран «Счета за месяц».

## Что сделано в тестовом задании

### 1. Расчёт долей по объёму (`lib/billing.php`)

Стоимость рейса делится между клиентами пропорционально объёму их груза (м³).

- **Всё считается в целых числах.** Стоимость переводится в копейки, объём в тысячные доли м³, вес в граммы. Дробных
  чисел в расчёте нет, поэтому нет и потерянных копеек. В рубли суммы переводятся только при выводе.
- **Метод наибольших остатков** (`distribute_cost`). Каждому клиенту сначала достаётся целая часть его доли, а
  недостающие копейки раздаются по одной тем, у кого остаток от деления больше. При равных остатках порядок задаёт
  `client_id`, поэтому повторный расчёт на тех же данных даёт тот же результат. Сумма долей всегда равна стоимости
  рейса до копейки.
- **Диспетчер `calc_share`** выбирает основу расчёта на рейс: по объёму, если объём указан и больше нуля у **каждого**
  груза рейса, иначе весь рейс делится по весу (см. «Решения»). В ответ добавлен признак `basis` (`volume` или `weight`).
- Общие шаги вынесены в `get_trip_cost_kop`, `get_trip_client_rows`, `distribute_cost`, `build_share_result`;
  `calc_share_by_volume` и `calc_share_by_weight` отличаются только единицами (тысячные доли м³ или граммы).
Старый расчёт терял копейки так: каждая доля округлялась отдельно (`round(cost * share, 2)`). В исходных данных это
три рейса: по ТВР-1103 в счетах на копейку больше стоимости рейса, по КЗН-1106 и СПБ-1107 на копейку меньше; в октябре недостача 0,02 ₽.

### 2. API долей рейса

`GET /api/trip_split.php?trip_id=11`: рейс, стоимость, клиенты (число грузов, вес, объём, доля, сумма, `basis`) и
`summary`: сумма по клиентам. Рейс не найден: `404`. `share` округляется до 4 знаков только для показа, суммы
берутся из целых копеек. `volume_m3` равен `null`, если объём не указан или не больше нуля.

### 3. Блок «Распределение стоимости» в карточке рейса

Таблица на jQuery (`public/js/trip_split.js`) заполняется из API: клиент, число грузов, вес, объём, на чём
распределено, доля %, сумма. Итоговые строки: «Итого по клиентам» и «Стоимость рейса». Прежний серверный блок
«Доли клиентов» заменён этим.

### 4. API счетов за месяц

- `GET /api/billing_preview.php?period=2026-10`: ничего не пишет. По каждому клиенту: `invoice_id`, статус счёта,
  `before`, `after`, `diff`, `action` (`create`, `recalculate`, `keep`); итоги `total_before` и `total_after`,
  итоги по действиям, стоимость рейсов месяца `trips_cost`, расхождения `vs_trips`, число реальных изменений `changes`.
- `POST /api/billing_apply.php` с `period=2026-10`: в одной транзакции создаёт недостающие счета (черновики) и
  пересчитывает черновики, **отправленные не трогает**. Черновик, который уже совпадает с новым расчётом, не
  перезаписывается, поэтому повторный вызов не меняет данные и не создаёт дублей. В ответе: создано, пересчитано,
  без изменений, пропущено и список счетов с действием.
- Суммы в ответах строками с двумя знаками, считаются в копейках. Период проверяется по маске `ГГГГ-ММ`.
### 5. Экран «Счета за месяц» (`public/billing.php`, `public/js/billing.js`)

Выбор месяца, «Показать», таблица «было / стало» по клиентам (сумма сейчас, по новому правилу, разница, статус),
итоги: общий, «будет создано», «будет пересчитано» (черновики), «не будет пересчитано» (отправленные, справочно) и
блок «Итоги за месяц» со сверкой со стоимостью всех рейсов. «Применить» активна, только если есть что менять, и
спрашивает подтверждение. После применения экран показывает результат и перезагружает предпросмотр.
Строки отправленных счетов серые, новых зелёные. Пункт «Счета за месяц» добавлен в меню.
Старая кнопка «Сформировать» (`billing_run.php`) теперь перенаправляет на новый экран: она перезаписывала и
отправленные счета.

### Итог «было и стало» и что он значит

- Общий итог по новому правилу равен стоимости рейсов (454 610,80), старый на 0,02 меньше. Но сами суммы по клиентам
  изменились сильно: деньги перераспределились от клиентов с тяжёлым грузом к клиентам с объёмным.
- Три черновика выросли в сумме на **63 092,12 ₽**. Три отправленных счёта остались прежними, а по новому правилу
  они должны были бы быть на **63 092,10 ₽** меньше (разница 0,02 ₽ это те самые потерянные копейки).
- Поэтому после применения сумма счетов за октябрь (**517 702,90**) на **63 092,10 ₽ больше** стоимости рейсов.
  Это не ошибка расчёта, а следствие решения не менять отправленные счета: клиентам с отправленными счетами
  (Родник, Мясной ряд, Пекарня Злата) выставлено по старому правилу, а черновики уже по новому.
  Как поступить с отправленными (корректировка, кредит-нота и т. п.), заказчик решит отдельно. Экран
  показывает эту разницу прямо в блоке «Итоги за месяц».
